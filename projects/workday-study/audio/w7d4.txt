Week 7, day 4. Security groups. [[slnc 1200]] Today's objective is Security Group Types, in the Security domain. [[slnc 600]] In one line: Choose the right membership method and constraint context. [[slnc 1200]] Let's start with the mental model. [[slnc 500]] Groups get members three ways: Workday-assigned (Workday defines and maintains members, such as Employee As Self and All Employees), manually assigned (administrators assign users, as in user-based groups), and derived (membership follows criteria such as role assignments, as in role-based groups). Role-based groups can be constrained or unconstrained. The context type describes what target data members can reach: unconstrained (no organizational limit), constrained to their own instance (self-service groups), constrained to public data, or constrained to the organizations where the member holds the role or belongs. A user’s access is the union of all their groups’ permissions. [[slnc 1200]] Now, the distinctions you need to know. [[slnc 500]] Role-based constrained: Role membership plus supported context. [[slnc 700]] User-based: Named maintained membership. [[slnc 700]] Workday-delivered: Workday-owned criteria. [[slnc 700]] Membership methods: Workday-assigned, manually assigned, derived. [[slnc 700]] Context type: What target data members can reach. [[slnc 700]]  [[slnc 600]] Here's how it shows up at work. [[slnc 500]] Use role-based constrained security for regional HR partners who should see only workers in organizations they support. [[slnc 1200]] Task and report names to recognize: Create Security Group, Assign Roles, and Assign Users to User-Based Security Group. [[slnc 1200]] And the exam trap to watch for. [[slnc 500]] Wrong constraint context can create broad access even when membership is correct. [[slnc 1500]] Quick check.
